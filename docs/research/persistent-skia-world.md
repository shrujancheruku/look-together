# Can expo-router keep one Skia world mounted behind route changes?

Research for [Research a persistent Skia world under expo-router](https://github.com/shrujancheruku/look-together/issues/147) (map [#142](https://github.com/shrujancheruku/look-together/issues/142)). Sources read on 2026-11-05, from the docs and source at these points:

- Expo: `expo/expo` `main` (2026-11-04), docs for SDK 58, [`bundledNativeModules.json`](https://github.com/expo/expo/blob/main/packages/expo/bundledNativeModules.json): `expo-router` ~58.0.26, React Native 0.88.1, `react-native-screens` ~4.30.1, Reanimated 4.7.1, `@shopify/react-native-skia` 2.14.0.
- React Native Skia: tag [`v2.14.0`](https://github.com/wcandillon/react-native-skia/tree/v2.14.0/apps/docs/docs) (the repo has moved to `wcandillon/react-native-skia`; `main` now documents v3).
- React Navigation docs 7.x and 8.x ([site repo](https://github.com/react-navigation/react-navigation.github.io)), Reanimated docs on `main`, React Native 0.88 docs and the `0.88-stable` source.

Anything marked **unverified** was not confirmed in a primary source. Anything marked **inference** is my reading of source code, not a documented promise.

Setup assumed: one Shoreline world ([ADR 0010](../adr/0010-we-render-our-own-pixel-art-world-without-a-game-engine.md)); every screen is a camera framing of it; text, input and accessibility stay native.

## Short answer

**Yes, on all three platforms, if the world lives in the root layout as a sibling *behind* the navigator, not inside any screen.** Expo Router's root `_layout` is never unmounted by in-app navigation, so a `<Canvas>` rendered there next to the navigator stays mounted for the whole session (a web reload remounts everything, as always). The route drives the camera by reading `usePathname()` / `useSegments()` in that layout and writing a camera target into a shared value.

Recommended shape:

1. **Root layout = `<World />` (absolute fill, opaque Skia canvas) + a navigator that draws nothing.** Use `Slot` (a `StackRouter` that renders only the focused route, no transition, identical on iOS, Android and web) or, if the Inquiry text needs a cross-fade while the camera pans, a small custom navigator from `createStandardRouterNavigator(…, StackRouter)` (stable in SDK 58). Avoid the native `Stack` for this layer: its screens, container and theme all paint `colors.background`, it has no `animation` on web, and its Android back is not predictive.
2. **Make every layer above the world transparent:** wrap in `ThemeProvider` with `colors.background: 'transparent'` (the Stack/Screen views read it), and `contentStyle: { backgroundColor: 'transparent' }` if any native `Stack` stays.
3. **Back:** Android hardware back still works through `BackHandler` on target SDK 36, but no navigator in SDK 58 gives *predictive* back except the alpha `ExperimentalStack` (which has no animation option and no web). Ship with predictive back off. Give the Recap no Back by how it is entered (`router.replace` / `dismissTo` so nothing Inquiry-side is under it) and by redirecting finished-Inquiry URLs, since the browser's Back can't be removed.
4. **Screen readers:** with no native transition, nothing tells VoiceOver or TalkBack that the "screen" changed. The app must move focus itself on each route change (`AccessibilityInfo.sendAccessibilityEvent(ref, 'focus')` on native, focus a heading and set the title on web).
5. **Scroll sync:** drive Skia-drawn panels from `useScrollOffset` (or `useAnimatedScrollHandler`) plus each panel's layout, all as shared values passed straight into Skia props. This runs on the UI thread on native and on the main thread on web. Whether it holds 60 fps with zero frame of lag between native text and the drawn panel is **unverified** and is the main thing to measure.

## 1. A persistent canvas behind the navigator

### Where it lives

- The root layout "represents the entry point for your navigation" and is where providers go ([layouts](https://github.com/expo/expo/blob/main/docs/pages/router/basics/layout.mdx)). Navigation only swaps what the navigator *inside* it renders, so a sibling of that navigator keeps its React state and native view. Nothing in the docs states this outright (**inference** from how layouts nest, consistent with the Slot example placing a header and footer around the route).
- **Don't put the world inside a screen.** A Skia canvas inside a screen that leaves the window can keep showing a stale picture on iOS when it comes back ([skia#4195](https://github.com/wcandillon/react-native-skia/issues/4195), open), and on web, canvases that mount and unmount with screens leaked whole WebGL contexts until 2.7.0 ([skia#3924](https://github.com/wcandillon/react-native-skia/issues/3924), fixed). One canvas that never unmounts sidesteps both.
- Expo's own [`with-skia` example](https://github.com/expo/examples/tree/master/with-skia) is the nearest first-party prior art: a `Slot` root layout and a lazily loaded full-screen Skia canvas under text. It keeps the canvas in one route, not behind the navigator.

### Which navigator

| | Native `Stack` | `Slot` | Custom navigator (`createStandardRouterNavigator`) |
|:--|:--|:--|:--|
| What it renders | Every pushed screen stays rendered ([layouts](https://github.com/expo/expo/blob/main/docs/pages/router/basics/layout.mdx)) as native screens; web renders all routes absolutely and hides unfocused ones with `display: 'none'` ([`NativeStackView.tsx`](https://github.com/expo/expo/blob/main/packages/expo-router/src/react-navigation/native-stack/views/NativeStackView.tsx)) | Only the focused route: `SlotContent` returns `descriptors[focusedRouteKey].render()` on a `StackRouter` ([`Navigator.tsx`](https://github.com/expo/expo/blob/main/packages/expo-router/src/views/Navigator.tsx)) | Whatever you render from `state` and `descriptors` ([custom navigators](https://github.com/expo/expo/blob/main/docs/pages/router/advanced/custom-navigators.mdx), stable in SDK 58) |
| Turning its own animation off | `animation: 'none'`: "Only supported on Android and iOS" ([RN 7.x native stack](https://github.com/react-navigation/react-navigation.github.io/blob/main/versioned_docs/version-7.x/native-stack-navigator.md)); Expo's Stack page lists `animation` as Android-only ([stack](https://github.com/expo/expo/blob/main/docs/pages/router/advanced/stack.mdx)), so iOS is **unverified**. Web never animates | Nothing to turn off | Nothing to turn off |
| Background | Paints `colors.background` on the screen stack container and each screen's content unless the presentation is `transparentModal` ([`NativeStackView.native.tsx`](https://github.com/expo/expo/blob/main/packages/expo-router/src/react-navigation/native-stack/views/NativeStackView.native.tsx)); web `Screen` paints it through `Background` ([`Background.tsx`](https://github.com/expo/expo/blob/main/packages/expo-router/src/react-navigation/elements/Background.tsx)) | Paints nothing | Paints what you paint |
| Back history | Stack | Stack (`StackRouter`) | Stack or tabs, and `extendRouter` / `extendRouterActions` to add actions |
| Hidden screens for screen readers | `aria-hidden` on native, `inert` on web, done for you ([`getUnfocusedScreenProps.ts`](https://github.com/expo/expo/blob/main/packages/expo-router/src/react-navigation/elements/getUnfocusedScreenProps.ts)) | Not needed (only one route is mounted) | Your job if you keep more than one mounted |

So `Slot` is the plain fit: it is a stack in history but draws nothing, so the world pans instead. A custom navigator is the step up if the outgoing screen's text should stay mounted to fade while the camera moves. Expo's `activityEnabled` / `<NavigationAwareActivity>` (experimental, SDK 58) can hide covered routes while keeping their state, if a native Stack is kept ([React Activity](https://github.com/expo/expo/blob/main/docs/pages/router/advanced/react-activity.mdx)).

A transparent native Stack is a known trap: on iOS `contentStyle: transparent` alone still shows a solid layer, and the fix users report is a transparent theme background ([expo#33040](https://github.com/expo/expo/issues/33040)), which matches the source above. `ThemeProvider` and `DefaultTheme` are exported from `expo-router` in SDK 58; since SDK 56 `@react-navigation/*` imports are not supported in app code ([SDK 55→56](https://github.com/expo/expo/blob/main/docs/pages/router/migrate/sdk-55-to-56.mdx)).

### The canvas itself

- Mark the world `opaque`. On Android that selects a `SurfaceView`, "the fastest path", which composites "correctly in React Native stacking order"; the non-opaque default is a `TextureView`, with an extra copy, a frame more latency, and stalls "during some view animations" ([Canvas, v2.14.0](https://github.com/wcandillon/react-native-skia/blob/v2.14.0/apps/docs/docs/canvas/canvas.md)). Canvases under React Navigation flickered on Android with `TextureView`; `opaque` was the reported fix ([skia#3459](https://github.com/wcandillon/react-native-skia/issues/3459), [skia#3713](https://github.com/wcandillon/react-native-skia/issues/3713)). Never use `zOrderOnTop`, which draws "above all React Native views in the window, including navigation screens".
- `onSize` takes a shared value for the canvas size on the UI thread ([Canvas](https://github.com/wcandillon/react-native-skia/blob/v2.14.0/apps/docs/docs/canvas/canvas.md)). Shared and derived values go straight into Skia props, and `select()` lets one object-valued shared value (a camera `{x, y, zoom}`) drive several props with one subscription ([animations](https://github.com/wcandillon/react-native-skia/blob/v2.14.0/apps/docs/docs/animations/reanimated3.md)).
- **Route → camera:** in the root layout, map `usePathname()` / `useSegments()` (both exported) to a camera target and animate a shared value to it with `withTiming`. Reanimated's default `ReduceMotion.System` makes `withTiming` jump straight to the target when Reduce Motion is on ([accessibility](https://github.com/software-mansion/react-native-reanimated/blob/main/docs/docs-reanimated/docs/guides/accessibility.mdx)), which is the cut the world wants then. A cold start or a web reload should set the camera without animating.

### Cost on web

- CanvasKit is 2.9 MB gzipped, loaded async; with Expo Router either `LoadSkiaWeb()` before `renderRootComponent` (needs your own `main` entry) or `<WithSkiaWeb>`, whose component must live outside `app/` in dev ([web](https://github.com/wcandillon/react-native-skia/blob/v2.14.0/apps/docs/docs/getting-started/web.mdx)). For a world under every screen, loading before the root renders is simpler.
- Browsers allow about 16 WebGL contexts per page; one persistent canvas uses one ([web](https://github.com/wcandillon/react-native-skia/blob/v2.14.0/apps/docs/docs/getting-started/web.mdx)). The web view loses and restores its context and builds one `GrDirectContext` per element ([`SkiaPictureView.web.tsx`](https://github.com/wcandillon/react-native-skia/blob/v2.14.0/packages/skia/src/views/SkiaPictureView.web.tsx)).
- On web, Reanimated is "implemented purely in JavaScript, hence the efficiency of the animations might be lower" ([web support](https://github.com/software-mansion/react-native-reanimated/blob/main/docs/docs-reanimated/docs/guides/web-support.mdx)). Skia's web container subscribes to shared values through Reanimated's `startMapper` ([`Container.web.ts`](https://github.com/wcandillon/react-native-skia/blob/v2.14.0/packages/skia/src/sksg/Container.web.ts)), so every camera frame redraws on the main thread alongside React. A 60 fps budget there is **unverified**.

## 2. Back on Android and in the browser, and a Recap with no Back

**Android hardware back.** `BackHandler` listeners run last-registered first; returning `true` stops the event, and if none does the app exits ([BackHandler 0.88](https://reactnative.dev/docs/backhandler)). React Navigation pops the focused stack by default and documents overriding it per screen with `useFocusEffect` ([Android back](https://github.com/react-navigation/react-navigation.github.io/blob/main/versioned_docs/version-7.x/custom-android-back-button-handling.md)). This works the same under `Slot` or a custom navigator, since it acts on the router.

**Predictive back.**
- Android 16 enables predictive back animations by default for apps targeting API 36, and stops calling `onBackPressed`; the opt-out is `android:enableOnBackInvokedCallback="false"` ([Android 16 changes](https://developer.android.com/about/versions/16/behavior-changes-16)). React Native 0.88 targets SDK 36 ([`libs.versions.toml`](https://github.com/facebook/react-native/blob/0.88-stable/packages/react-native/gradle/libs.versions.toml)).
- React Native 0.88's `ReactActivity` registers an always-enabled `OnBackPressedCallback` on SDK 36 to keep calling `onBackPressed` ([`ReactActivity.java`](https://github.com/facebook/react-native/blob/0.88-stable/packages/react-native/ReactAndroid/src/main/java/com/facebook/react/ReactActivity.java)). So `BackHandler` keeps working, but the system can't preview back-to-home (**inference**).
- React Navigation 7.x and 8.x: "React Navigation doesn't yet support Android's predictive back gesture", so disable it ([getting started](https://github.com/react-navigation/react-navigation.github.io/blob/main/versioned_docs/version-8.x/getting-started.md)). Expo's toggle is `android.predictiveBackGestureEnabled` (default `false`, maps to that attribute; [app config schema v58](https://github.com/expo/expo/blob/main/docs/public/static/schemas/v58.0.0/app-config-schema.json)). With it on, Expo Router back gestures went to the home screen; Expo closed this as "won't be fixed in react-native-screens v4 … should be fixed once react-native-screens v5 is stable" ([expo#39092](https://github.com/expo/expo/issues/39092)).
- `ExperimentalStack` (alpha, SDK 56+) "ships with predictive back gesture support" but ignores `animation`, has no transparent modal, can't be mixed with `Stack` on Android, and falls back to `Stack` on web ([Experimental Stack](https://github.com/expo/expo/blob/main/docs/pages/versions/v58.0.0/sdk/router/experimental-stack.mdx)). It's no use for a world that pans instead of screens sliding.
- **So: keep `predictiveBackGestureEnabled: false`.** A world that pans has no system animation to preview anyway; a predictive pan of the camera would be custom work on `OnBackAnimationCallback`, and nothing in these libraries exposes it (**unverified** that any does).

**Browser back and reload.**
- Browser Back fires `popstate`, which Expo Router treats as navigation. If the leaving screen prevents removal, the router moves the browser back to the entry matching the UI with `history.go(delta)` ([`browserHistory.ts`](https://github.com/expo/expo/blob/main/packages/expo-router/src/global-state/browserHistory.ts), **inference** from source). On web `usePreventRemove()` also asks for confirmation on refresh or tab close ([prevent screen removal](https://github.com/expo/expo/blob/main/docs/pages/router/advanced/prevent-screen-removal.mdx)). It does not cover leaving the app ([`usePreventRemove` limitations](https://github.com/react-navigation/react-navigation.github.io/blob/main/versioned_docs/version-7.x/use-prevent-remove.md)).
- Reload remounts the app from the URL, so every route's camera framing must come from the URL and the stored records, not from where the camera was.

**The Recap with no Back.** Recommended, in order:
1. Enter it with `router.replace` or `router.dismissTo('/')` + push, so the stack under the Recap is the Landing, not the Inquiry. `dismissTo` "dismisses screens … until the specified `Href` is reached" ([stack](https://github.com/expo/expo/blob/main/docs/pages/router/advanced/stack.mdx)). Android back on the Recap then goes to the Landing, which is where the Recap opens in the world anyway (Glossary: Landing).
2. On web, older browser entries for that Inquiry's Probes and Path can't be deleted. Make those URLs redirect to the Recap (or the Landing) once the Inquiry has finished, from the stored records. `Stack.Protected` redirects guarded routes to the anchor ([protected routes](https://github.com/expo/expo/blob/main/docs/pages/router/advanced/protected.mdx)), but its guard is per route, not per Inquiry, so a `<Redirect>` inside the screen fits better.
3. Don't trap Back with `usePreventRemove` on the Recap. React Navigation recommends using it sparingly ([`usePreventRemove`](https://github.com/react-navigation/react-navigation.github.io/blob/main/versioned_docs/version-7.x/use-prevent-remove.md)).

## 3. Screen-reader focus when only the world moves

- No navigator in SDK 58 moves focus on a route change. Searching `expo-router/src` finds no `AccessibilityInfo`, `setAccessibilityFocus` or `.focus()` outside the search bar and the JS stack's keyboard manager. The native Stack only hides unfocused screens (`aria-hidden` / `inert`, above).
- Native stacks leave initial focus to UIKit and Android and get it wrong today. On iOS, a programmatic focus after a native-stack push is "delayed, overridden by the automatic first focus, or occasionally not honored"; maintainers confirm it and won't fix it soon ([screens#4819](https://github.com/software-mansion/react-native-screens/issues/4819), open). Focus also resets to the first element on going back ([react-navigation#11189](https://github.com/react-navigation/react-navigation/issues/11189), open).
- Under `Slot` or a custom navigator there is no native transition, so VoiceOver and TalkBack get no screen-change signal at all (**inference**). The app has to:
  - On native, after the route's content mounts, call `AccessibilityInfo.sendAccessibilityEvent(headingRef, 'focus')` on an `accessible` heading ([AccessibilityInfo 0.88](https://reactnative.dev/docs/accessibilityinfo); `setAccessibilityFocus` is deprecated in its favour). Use `announceForAccessibility` for world-only changes (a pad unfurls); on iOS it can queue behind current speech.
  - On web, focus the route's heading (`tabIndex={-1}`) and update the document title through `expo-router/head`. That react-native-web passes `tabIndex` and `.focus()` through cleanly is **unverified**.
  - Keep the world canvas out of the accessibility tree (no `accessible` on it), so the only thing announced is native text.
- Having one focus routine in the root layout, keyed on the pathname, also gives TalkBack and VoiceOver the same behaviour, and is a small module to test.

## 4. Native text scroll in sync with Skia-drawn panels

- `useScrollOffset(animatedRef)` returns a shared value with the offset of a `ScrollView`, `FlatList` or `FlashList` on Android, iOS and web. `useAnimatedScrollHandler` works on all three, but "only `onScroll` event works on Web" ([useScrollOffset](https://github.com/software-mansion/react-native-reanimated/blob/main/docs/docs-reanimated/docs/scroll/useScrollOffset.mdx), [useAnimatedScrollHandler](https://github.com/software-mansion/react-native-reanimated/blob/main/docs/docs-reanimated/docs/scroll/useAnimatedScrollHandler.mdx)).
- Pattern: each panel reports its layout with `onLayout` into a shared value, or with Reanimated's `measure` (all three platforms). The world derives `panelY = layoutY − scrollY` in a `useDerivedValue` and passes it to the Skia panel. Nothing crosses to the JS thread on native, and Reanimated warns against reading shared values on the JS thread ([performance](https://github.com/software-mansion/react-native-reanimated/blob/main/docs/docs-reanimated/docs/guides/performance.md)).
- Known jitter: scroll-driven animations flicker on the New Architecture unless `preventShadowTreeCommitExhaustion` and `DISABLE_COMMIT_PAUSING_MECHANISM` are on (RN ≥ 0.81). FPS drops while scrolling are fixed by `USE_COMMIT_HOOK_ONLY_FOR_REACT_COMMITS` (Reanimated ≥ 4.2) ([performance](https://github.com/software-mansion/react-native-reanimated/blob/main/docs/docs-reanimated/docs/guides/performance.md)). Those fixes apply to Reanimated-styled views. A Skia canvas reading a shared value skips the shadow tree, so it likely avoids that path (**inference**).
- **Unverified, measure first:** whether the Skia redraw lands in the same frame as the native scroll view's move, or one frame behind. No doc or issue in Skia or Reanimated states it. A one-frame lag shows as the drawn panel trailing the text on fast flings. If it does, fall back to plain native views (or a small per-panel canvas inside the scroll content) for panels that scroll with text, and keep the world for what doesn't scroll.
- Snap scroll-driven positions to whole art pixels in the derived value, as with all world motion, so sub-pixel scroll doesn't shimmer the pixel art.

## 5. Prior art

- Expo [`with-skia`](https://github.com/expo/examples/tree/master/with-skia): a full-screen Skia canvas under RN text, lazily loaded on web, in one route under a `Slot`.
- Skia's docs show shared values driving canvases from `useFrameCallback` and gestures, but no example under a navigator. No first-party Expo, React Navigation, Skia or Reanimated example of a persistent animated background *behind* navigation was found (**unverified** that none exists). Community transitions libraries exist but aren't primary sources and weren't relied on.

## Open questions to settle in the prototype

1. Same-frame or one-frame-late: native `ScrollView` offset → Skia panel, on a Pixel 8 Pro, a mid-range Test Lab device, iOS, and Chrome/Safari.
2. Camera pan at 60 fps on web while React renders the incoming route's text.
3. VoiceOver and TalkBack: does `sendAccessibilityEvent(…, 'focus')` after a `Slot` route change land reliably (no native transition to fight, unlike screens#4819)?
4. Does `animation: 'none'` on the native Stack honour iOS (the two docs disagree), if a native Stack is kept anywhere?
5. Cold start on web: the cost of `LoadSkiaWeb()` before first paint, versus showing native text first and fading the world in.
